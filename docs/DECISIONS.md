# Журнал решений

Коротко: что решили, почему, что отвергли. Новые записи — сверху.

## 2026-09-04 · Модель ИИ выбрана замером, не по памяти

Первый день на `claude-haiku-4.5` стоил $14.5 за 15 499 комментариев: каждый комментарий — отдельный вызов с
инструкцией и разбором поста. Контрольный прогон (`app/services/ai/bench.py`, 300 комментариев с эталоном haiku,
60 постов, 60 кандидатов, $0.71 на всё):

| модель | комментарии по одному | комментарии пачкой по 20 | $/1000 пачкой |
|---|---|---|---|
| claude-haiku-4.5 | эталон | 96.3% | 0.381 |
| **gemini-2.5-flash-lite** | 70.7% | **98.3%, точность 99.4%, 0 сбоев** | **0.025** |
| deepseek-v4-flash | 98.5% | 100%, но 100 сбоев из 300 (пустой/битый JSON) | 0.016 |
| qwen3-235b | 69.7% | 84.7% | 0.026 |
| gpt-5-nano / gpt-5-mini | пустой ответ: рассуждающие модели требуют отдельного параметра | — | — |

Решение: комментарии — gemini-2.5-flash-lite **пачкой по посту** плюс правила до ИИ (голый «+», кодовое слово,
эмодзи, @упоминание); посты — gemini-2.5-flash-lite (по категории и кодовому слову ближе к ручной разметке, чем
haiku); кандидаты «кто и где» — haiku (дешёвые модели совпадают по городу на 77–87%, объём мал). Модели — в
настройках `ai_model.*`, меняются без деплоя.

Побочный вывод: в xlsx заказчика «нет категории» не значит «непродающий» — все модели одинаково расходятся с
таблицей на явно продающих постах; эталоном для постов таблицу не считать.

## 2026-09-03 · Воркеры и поправка про кириллицу

**Кириллица в `links` parser.im работает.** Ранний вывод «любой не-ASCII → 500» был сделан по полям `name` и
`white_comment_text`; хэштеги и ключевые слова в UTF-8 принимаются. ASCII-запрет в клиенте сужен до `name`.
Без этого поиск по #риелтормосква был бы невозможен.

**Один выключатель сбора** (`collection_enabled`, Настройки → Управление). Пока он выключен, воркеры не создают
заданий p1/p2 и не ходят в Apify — можно спокойно заводить доноров и задачи поиска, ничего не тратя.
Поиск доноров (p3/p5/f1) работает всегда: его запускает оператор руками.

**Посты без города не собираем.** У неразобранного донора ИИ определяет город по посту; не определила —
пост ждёт. Лид без города некуда отдавать, а строки parser.im на него уйдут.

**Первый сбор для импортированной базы — тот же путь, что для нового донора:** продающие посты за `intake_days`,
у которых ещё не было сбора. 973 московских поста ≈ 98 заданий p2 по 10 ссылок, при 10 строках — часы, не дни.

**ИИ — `anthropic/claude-haiku-4.5` через OpenRouter**: пост ≈ $0.0015, комментарий ≈ $0.001. На московские
объёмы (~20 тыс. комментариев/сутки без ответов донора) — ~$20/день; при необходимости режется правилами до ИИ.

## 2026-09-03 · Крупные посты — Apify (проверено)

`apify/instagram-comment-scraper` отдаёт комментарии **от новых к старым** (14 из 14 пар по убыванию),
15 строк за 6 секунд, последний комментарий — за 27 минут до запуска. Значит досбор на посте с 13 тыс.
комментариев — это `resultsLimit` ≈ вчерашний прирост × 2, секунды и доли цента, а не 45 минут строки
parser.im. Порог «крупный пост» — настройка `big_post_threshold` (1000). Первый сбор и обычные посты —
по-прежнему parser.im `p2 web=1`.

Аккаунт Apify — тариф FREE ($5 кредитов в месяц). Для боевого суточного цикла (~$2/день на город) нужен Starter.

## 2026-09-03 · Поправки v2 → v3 и результаты замеров

**Окно постов при заводе донора — настройка** (`intake_days`), не константа 45: старые посты могут уже не
давать комментариев.

**Неразобранные доноры — отдельная ветка, город по постам.** Кому ИИ не смогла назначить город (или два города
в шапке), посты всё равно собираем; ИИ по каждому продающему посту определяет город, и пост уходит в свой город
как источник. Донор остаётся без города.

**Отсев по виду деятельности** на этапе ИИ по имени и описанию: риелторы, застройщики, агентства — берём;
ипотечные брокеры, стройка, ремонт — нет. Критерии — в промпте, правятся в настройках.

**Никакого `dop` и фильтров по автору в сборе комментариев.** Замер: с `dop` 3.6 комм/мин, без — 17, с `web=1` — 318.
Телефоны из инстаграма не берём вовсе (могут быть номера администраторов), только пробив.

**Досбор на крупных постах — решение отложено** до проверки, отдаёт ли Apify свежие комментарии первыми.
parser.im отдаёт от старых к новым, «только новые» у него не получить. При 318 комм/мин мега-пост на 13 тыс. —
45 минут одной строки; терпимо для единиц, не для десятков.

**Референс интерфейса — Mixpanel** (светлая тема, левое меню, фиолетовый акцент, карточки, таблицы с моно-цифрами).

## 2026-09-03 · Поправки заказчика после прототипа v1 → v2

**Две петли, не одна.** Новый донор проходит разовую: `p1` посты за 45 дней (parser.im, не Apify —
подписка), ИИ-разметка, первый сбор `p2` по всем продающим с отсевом по дате комментария. Потом —
на монитор: Apify смотрит только новые посты и прирост, `p2` досбирает по приросту.

**Пробив — внутри города.** Отсеки «непробитые / пробитые», выбор актуальности (пресет или даты),
ручной или авто-режим, токен задачи пробива, постбек. На сервис пробива уходит вся строка (логин,
город, комментарий, дата, url поста, разбор), а не голый логин. Проверка базы — у нас, до отправки:
номер есть → платный запрос не тратим.

**Лиды в CRM шлёт этот сервис**, не сервис пробива. Статусы обратно — по lead_id, поле добавит заказчик.

**«Топ» доноров убран.** По постам/комментам он ничего не даёт; единственный осмысленный рейтинг —
стоимость лида по донору, появится со статусами. Сиды для рекомендаций оператор выбирает галочками.

**Экраны — списки по всем городам с фильтром**, не провалы город → донор → пост. Экрана
комментаторов нет: кто что написал — статистика, ИИ сегментирует; интересна динамика по дням.

**Расписание кронов настраивается.** Порядок утром: новые посты → прирост → досбор.

**Бот оповещений без chat_id** — запоминает, кто нажал /start.

## 2026-09-03 · Поправки заказчика после прототипа

**Теги и ключи — глобальные, не по городам.** Город — результат цепочки поиск → f1 → ИИ →
подтверждение, а не вход. Из города стартуют только рекомендации (сиды — его топ по комм/1000),
и их результат тоже раскладывается по городам заново.

**Посты — целиком Apify, parser.im их не трогает.** Тариф parser.im — 10 одновременных строк
(логинов / тегов / ссылок), это главное ограничение. Постов мало (~33/сутки на город), на Apify
они стоят копейки; строки нужны под комментарии, фильтр и поиск — в таком приоритете.

## 2026-09-03 · Стек

**Бэкенд — Python/FastAPI, не Node/Hono.**
У заказчика есть другой сервис на Node + Hono + Prisma + React/Mantine — он работает, но это другая
система, и связи с ней у нас нет кроме HTTP. Для этой задачи (пакетный разбор текстовых выгрузок,
bulk-вставки миллионов строк, ИИ-вызовы) Python естественнее, а рабочий клиент parser.im, дедуп
и фильтры уже написаны и проверены на боевых данных в модуле мониторинга старого сервиса.

**Фронт — React + TypeScript + Vite + Mantine + TanStack Query.**
Отверг Vue через CDN без сборки: для дашборда с фильтрами по городам и периодам нужны таблицы,
дата-пикеры и графики из коробки. Mantine всё это даёт. Совпадает со стеком другого сервиса
заказчика — будущий разработчик не встретит ничего нового. Сборка — на сервере в скрипте деплоя.

**Без Redis.** Очередь заданий живёт в PostgreSQL (`FOR UPDATE SKIP LOCKED`). Лимит 180 запросов/мин
к parser.im считается в памяти воркера — он один. Redis добавил бы службу без задачи.

**Без Docker и Coolify.** Один сервер, администрируем по SSH. systemd + nginx + скрипт деплоя
прозрачнее: логи в `journalctl`, процесс виден напрямую. Если понадобится Coolify — контейнеризация
тривиальна, но не сейчас.

**Отдельный сервис и БД.** Не модуль внутри старого `pyrogram-bot`: там один SPA-файл на 130 КБ
с глобальными функциями и миграции через `try/except: pass` — заказчику это не нравится, и мне тоже.
Изоляция нагрузки: миллионы комментариев не должны делить SQLite с очередью пробива.

## 2026-09-03 · Инфраструктура

**Два сервера.** Старый (`132.243.114.17`, 1 CPU / 1.8 ГБ) остаётся под пробив: Telegram-сессии
привязаны к IP, при переезде возможен повторный вход, а доставка кодов на эти номера уже ломалась.
Новый (`95.81.103.196`, 4 CPU / 7.7 ГБ / 80 ГБ) — под лидген. Оба в Амстердаме у одного провайдера,
0.36 мс между ними.

**Локация не РФ.** OpenAI режет российские IP; OpenRouter, Apify и GitHub без IPv6.
Публичный IPv4 обязателен.

**ISPmanager снесён.** Владел nginx, поднял BIND на публичном IP:53 (открытый резолвер —
риск amplification и блокировки от хостера). Заказчик панелью не пользуется.

## 2026-09-03 · Логика сбора

**Apify — только ежедневное и точечное.** Схема «Apify каждые 3 часа по 3-месячному окну постов»
из первоначального ТЗ стоила бы $12–55 тыс./мес на 300 донорах: платишь за перечитывание одних и тех же
комментариев до оплаты дедупликации. parser.im отдаёт только новое по подписке.

**parser.im — тяжёлое и разовое.** `p2 act=3` принимает ссылки на конкретные посты и отдаёт дату
комментария → весь сбор комментариев на подписке. Мониторинг `m1` не используем: держит слоты вечно,
разовые задания их освобождают.

**Фильтрация — отдельным заданием `f1`, не во время сбора.** Встроенная фильтрация parser.im
работает слишком медленно (наблюдение заказчика).

**Фильтр «коммерческий пост» — на этапе скачивания комментариев, не сбора метаданных.**
Метаданные постов профиля стоят одинаково независимо от классификации. Плюс страховка: у некоммерческого
поста скачок счётчика → всё равно берём (вирусный рилс).

**Ключевые слова, чёрный список, дубли — считаются у нас.** API parser.im отвечает 500 на любой
не-ASCII символ в параметрах (и при этом создаёт задание без фильтра). Кириллицу туда не шлём.
Побочный плюс: настройки меняются на лету без пересбора.

## 2026-09-03 · Данные

**Единый справочник `ig_accounts`** для доноров и комментаторов. Отсюда «уже пробитых отдаём сразу».

**Два разных правила повторов.** Пробив — никогда дважды (номер в базе). Отдача в CRM — повторно можно,
но не чаще `resend_after_days`: человек мог откликнуться на новый оффер через два месяца.

**Цены — снимком в лид.** Иначе смена тарифа перепишет всю историю конверсий задним числом.

**Статусы из CRM — по `lead_id`, не по логину.** При повторной отдаче того же человека статус
ляжет на нужную карточку.

**Inbox/outbox.** Приём вебхука: записал сырое тело, ответил 200, разбор воркером. Отправка: лид и запись
в outbox одной транзакцией, ретраи с растущей паузой. Ни одно событие не теряется из-за падения разбора.

**Донор в нескольких городах** — связь многие-ко-многим через `lg_donors`.

**Карантин новичка.** Донор не попадает в ежедневный обход сразу: 45 дней постов → медиана → порог.
Общая медиана по 1484 постам — 7, у топ-источников 197–312. Порог 30 отсекает мусор, не задевая рабочих.

**Сиды для рекомендаций — по комментариям на 1000 просмотров**, не по сумме комментариев.
Сумма поощряет большой охват, нормированная метрика — тех, кто реально цепляет.

## Отвергнуто

- Celery/Redis/RabbitMQ — нет задачи.
- Прямой реверс Instagram — ломкость, баны, есть парсеры.
- Хранить все комментарии вечно с текстом — текст мусора чистится через 30 дней, id остаётся.
- Apify для мега-постов — 37 постов с 65% комментариев при перекачке целиком дали бы $60/день.
