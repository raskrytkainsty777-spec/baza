# parser.im — что знаем про их API

Проверено запросами 01–03.09.2026. Базовый URL `https://parser.im/api.php`, ключ в `key`, GET или POST.
Лимит 180 запросов в минуту, при превышении 429.

## Квирки, из-за которых код выглядит так, как выглядит

**Любой не-ASCII символ в параметрах роняет их бэкенд.**
- кириллица в `name` → 500, задание **не** создаётся;
- кириллица в `white_comment_text` → 500, но задание **создаётся** — без фильтра, молча;
- латиница везде → работает.
Поэтому имя задания транслитерируем, ключевые слова и стоп-слова в API не шлём, фильтруем у себя.
После неудачного `create` сверяемся со списком заданий (`mode=status&status=7`) — задание могло
создаться вопреки ошибке.

**Выгрузка `mode=result` — не JSON.** Текст с BOM, первая строка — заголовок колонок через `:`,
дальше строки данных. Двоеточия внутри значений они экранируют сами (`https://` → `https_//`,
`21:12` → `21.12`), так что `split(':')` безопасен. Пример заголовка p2: `source:id:login:text_comment:date_comment`.

**Удаление отрабатывает не сразу.** `mode=delete` отвечает `ok`, но в списке задание висит ещё
несколько минут.

**Фильтрация во время сбора медленная** — фильтруем отдельным заданием `f1`.

**Мониторинг `m1` держит слот вечно** — используем только разовые задания.

**`white_*` принимает URL к TXT-файлу** (до 350 000 строк), но только по https; http на голый IP → 400.
Для нас неактуально: фильтруем у себя.

## Типы заданий, которые используем

| Тип | act | Что делает | `links` | `spec` / `dop` |
|---|---|---|---|---|
| `p3` | 5 | авторы постов по хэштегам | хэштеги через запятую | `spec=1,2` id+логин |
| `p5` | 5 | авторы постов по ключевым словам | слова через запятую | `spec=1,2` |
| `f1` | — | фильтрация и догрузка по списку аккаунтов | логины, **или id задания-источника**, или URL txt | `spec=1,2`; `dop=1,2,3,5,6,8,20,21,22` телефон, email, имя, город+адрес, описание, подписчики, подписки, постов, дата последнего поста |
| `p1` | 6 | посты с аккаунтов | логины/ссылки аккаунтов | `spec=1,2,4,5,6,7` id поста, URL, описание, лайки, комментарии, дата; `limit2` — на аккаунт |
| `p2` | 3 | комментарии с постов | **ссылки на посты** или аккаунты | `spec=1,2,3,4,6` id автора, логин, id комментария, текст, дата; `dop=1,2` телефон/email автора; `posts_limit`, `postdate` |

Полезные фильтры `f1` / `p2` по автору: `lastpost` (дней с последнего поста), `followers1/2`,
`followings1/2`, `posts_zero`, `private`, `white_bio`, `white_address`, `kfc1/2` (вовлечённость
по комментариям, %). Всё — ASCII-only.

Ответы: `{"status":"ok","tid":"123"}` (tid может быть списком через запятую), `{"status":"error","text":"…"}`.
Статус: `mode=status&tid=…` → `tid_status` ∈ in progress / suspended / completed / error / queue.

## Что ещё не проверено

- Формат `f1` в `mode=result`.
- `web=0` против `web=1` у остальных типов (p1, p3, p5, f1) — где быстрее. Замерить при первом боевом прогоне.
- Скорость `p2` на задании с 50+ ссылками на посты.
- С докупкой строк (100 вместо 10) суточный цикл перестаёт быть узким местом вовсе.

### Что показала фаза 0 (03.09.2026)

**Форматы выгрузок — подтверждены, все строки разбираются `split(':')` без потерь.**

- `p1 act=6` → `source:post_id:post_url:post_text:post_likes:post_comment:post_date`. Дата `18.01.2025_17.58`.
  `limit2=40` отдаёт 40 постов, но **сверху закреплённые** (могут быть 2024–2025 года), остальное свежее —
  порядок не хронологический, окно по дате режем у себя. Покрытие 45 дней: 26–40 из 40 у активных доноров.
  Скорость: 8 аккаунтов × 40 постов = 320 строк за ~35 мин.
- `p2 act=3` (+`dop=1,2`) → `source:id:login:id_comment:text_comment:date_comment:phone:email`.
  `id_comment` — ключ дедупа. Комментарии идут **от старых к новым**. Пустой телефон = `0`.

**Телефон/email в `dop` заполнены у 11–16% комментаторов** (258 + 71 строк). **Не используем** — решение
заказчика: в профилях могут быть номера администраторов, телефоны только через пробив. Да и скорость.

**Скорость `p2` — всё решает `dop` и способ сбора** (один и тот же пост на 8 355 комментариев):

| Вариант | Скорость |
|---|---|
| `dop=1,2`, mob api | 1–3.6 комм/мин |
| без `dop`, mob api (`web=0`) | 17 комм/мин |
| без `dop`, **`web=1`** | **318 комм/мин** (3000 за 9 мин) |

Вывод: сбор комментариев только `web=1` и без `dop`/фильтров. 1000 комментариев ≈ 3 минуты,
мега-пост на 13 767 ≈ 45 минут одной строки.

**Порядок комментариев — от старых к новым** (ветки ответов вперемешку). `limit` отдаёт самые старые,
«только новые» на их стороне не получить — досбор на посте = перекачка целиком, отсев по `id_comment` у нас.

**Ответы самого автора — 49% строк** на этом посте (1459 из 3000: риелтор отвечает каждому). Флаг
`is_donor_reply` режет половину объёма ещё до ИИ.

**Тариф: 10 одновременных строк** (логинов / тегов / ссылок на посты). Сверх — очередь. p1 на 8 логинов + p2 на 3 ссылки → третье задание встало в очередь.
